# POS screen stability and release procedure

The first candidate is based on production main a17806f. This work has no database migration and does not alter Android Java, APK settings, Stripe provider/coordinator, refund allocation, or driver accounting. Native JavaScript bridge and print/checkout lifecycle code acquire update guards; the underlying operations and their idempotency keys are unchanged.

## Evidence and limits

Two reproduced defects: the old update timer reloads 900 ms after an idle check even if an order/payment starts meanwhile; and a delayed older HTML response overwrites newer offline HTML. The former manual reload bypasses all busy checks. The former newest-tab-wins ownership policy also unmounts an active register immediately. The background RSC refresh can hard-navigate on Next deployment skew (documented Next behavior), bypassing the app update policy.

These are verified software paths, not proof of what occurred on the physical Elo. No device trace establishes whether a particular incident loaded older JavaScript, restored older application state, or involved another register/display. More → This app and privacy-safe `app.update_state`, `app.reload`, `app.update_confirmed`, `app.asset_load_failed`, and `app.competing_instance` logs now distinguish these events. No order contents, payment credentials, signatures, URL query values or customer identities are added to these logs.

Android review: one singleTask activity/WebView; no restoreState; release URL fixed to https://app.hanafymedia.com/pos; no resume/reconnect reload; LOAD_DEFAULT cache and APK-version-only cache clearing. Back/forward can restore a previous document, so pageshow also verifies the live build. Native Java/APK changes are unnecessary for the reproduced defects. The native main-frame error page does retain an existing ten-second retry to the release URL after a navigation fails; it is not a resume/reconnect handler and does not fire inside a successfully loaded document. It can reopen an offline copy after a failed navigation, so target receipts and the software retry limit must be checked on the device. Physical lifecycle, reader, caller ID and printer acceptance remains unperformed.

The existing PostCSS build transform flattens Tailwind cascade layers for older WebViews. There is no separate legacy stylesheet now; this transform and CSS are unchanged. No device trace proves a CSS regression in the reported incidents.

## Running sessions

One update manager per document polls no-store version identity at startup, each minute, on visibility/pageshow/reconnect. It tracks full loaded/server build IDs, commit, build time and API/bridge contracts. JSON runtime refresh replaces POS router.refresh and only applies data from the loaded build while still idle. Next deploymentId versions asset URLs; immutable asset caching remains keyed by the complete URL. POS HTML is no-store; offline HTML is explicitly stamped and serialized cache writes reject older builds. Worker activation does not reload the page. Offline drafts and their existing storage keys are retained.

Local guards read live order/payment/call/sync/tip/print state, focused inputs/dialogs, background/offline state, native promises, checkout steps and mutating requests. Native timeouts and ambiguous financial transport outcomes remain blocked until a definitive late result or successful idempotent recovery. The print station also checks its pending durable queue. A read-only, authorized, workspace-scoped server check covers pending payments, refunds, tips and hold releases. A non-print-station device does not wait for another register's printer backlog.

After one minute without interaction and no blockers: schedule 900 ms, recheck, refetch live identity, verify durable work, verify storage, persist reload receipt, then synchronously recheck every guard/activity revision immediately before reload. There is no asynchronous gap after the last check. A target-bearing navigation cannot fall back to a different cached build. The next document confirms its target. At most two attempts per target in 30 minutes; unresolved identity/storage/bridge/operation failures show an actionable status instead of restarting repeatedly. Retrying a failed financial request uses the existing payment recovery flow; the update manager never retries a charge.

An exclusive browser Web Lock owns the register until its document closes. A second tab waits without mounting POS hardware/sync/checkout. Closing the owner hands ownership to the waiting tab. No takeover button can interrupt active work. Unsupported WebView versions fail closed with an upgrade instruction. This is per browser profile; different apps/profiles still require distinct register names and the existing server display-publisher ownership controls.

The first rollout cannot retrofit guards into already running legacy JavaScript. At a quiet cutover, finish payments/orders and close duplicate legacy tabs before opening the new build once. Do not clear app data or saved drafts. Subsequent updates use the managed lifecycle.

## Compatibility and future release gates

API contract 1 accepts legacy client 0 and client 1. POS mutations outside the declared compatibility window return 409 APP_UPDATE_REQUIRED before starting work. Provider webhooks are excluded. Bridge contract 1 requires existing printerSend/stripeCollect methods; browser sessions have no Android bridge requirement. Additive changes must retain the previous API and draft/database format through the transition; incompatible releases must deliberately raise contract/minimumClient and provide a separately reviewed database/native compatibility plan. A contract number does not automatically prove database compatibility.

GitHub Actions runs lint, typecheck, the complete Vitest suite (including PostgreSQL tests) and build. Configure its successful status as a required branch protection check if not already required; this repository change alone cannot enforce repository administrator permissions. Browser/staging validation remains an explicit release gate with isolated authenticated test fixtures.

The Vercel ignored-build step checks actual live identity and Git ancestry before building production main. Unknown identity, missing history or a candidate lacking the live commit cancels promotion. One exact legacy live build ID maps to its independently verified a17806f baseline for the first rollout; every new build publishes the full identity. Staging is exempt only for the existing staging app URL AND isolated Supabase URL pair. Do not change these to production destinations. Vercel administrator manual alias/rollback actions can bypass Git/ignored-build safeguards; no code change can revoke those privileges. Build-time checks also cannot eliminate a simultaneous operator promotion race. Serialize production promotions and verify the alias immediately before and after cutover.

Before requesting production approval:

1. Fetch main. Review any drift; preserve payment stabilization and customer checkout commits. Run all software checks on the exact candidate and record results.
2. Verify staging is free and isolated (sandbox Stripe, isolated Supabase, outbound integrations off, scheduled capture disabled). Deploy the exact pushed commit. Verify /api/version commit/build/contract and Vercel Git source. No migrations for this candidate.
3. Run staging browser workflows, customer checkout regression, and screen-stability tests. `E2E_UPDATE_CONTROL_DIR` points to a private temporary directory. The real transition test writes browser-ready.json with build A; deploy the SAME candidate again to staging, then write target.json containing build B. The test verifies an open order delays updating, explicitly closes only its synthetic order, observes automatic idle navigation to B and confirms a single reload receipt. Verify sandbox totals and restore staging test settings/capture disabled.
4. Run `node scripts/verify-release.mjs --candidate FULL_SHA --staging https://waynes-pos-staging.vercel.app` from a clean checkout. This is read-only and verifies latest main/live ancestry and exact staged identity. Stop on drift. Obtain approval for that full SHA.

After approval: arrange a quiet moment, reconcile pending financial work, preserve backups/drafts, close legacy duplicate sessions, fast-forward reviewed main normally, and let the existing production Git deployment run. Immediately verify READY deployment Git SHA, /api/version identity, schema unchanged, login/order/POS/payment authorization, financial pending counts and logs. Confirm the actual Elo's loaded/server IDs and native diagnostics. Never use a customer card for a test.

If cutover fails: stop new financial initiation and scheduled captures using the established financial containment runbook; inspect/reconcile existing idempotent operations and provider references before resuming. Do not erase records, force refund/capture state, clear saved orders, or apply reverse database migrations. Prepare a tested forward revert commit containing the current production history; do not silently repoint the alias to an older build. A privileged emergency alias rollback is a separately coordinated exception requiring compatible database/API contracts and a safe register restart. The timestamp high-water guard intentionally blocks silent older builds.
