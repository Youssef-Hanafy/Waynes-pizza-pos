# Stage 2: shared reads and live notifications

This stage reduces repeated reads without changing card capture or payout processing.

- Alerts, the current-order rail, Payments and Open Orders share one workspace/location-scoped open-order feed. Concurrent reads share a request. An action or live event arriving during a read schedules a follow-up read. One visible-page minute fallback is reference-counted across consumers; reconnect/visibility return resyncs the feed. Failed reads preserve the last orders and do not seed historical-order alerts.
- Customer screens and registers subscribe to an authenticated revision-only notification table. Existing permission-checked RPCs still carry screen state, tip answers and signatures. Real state/answer/publisher changes notify; heartbeat/read writes do not, avoiding feedback loops. Healthy links use 30-second heartbeats, with server screen-liveness tolerance of 90 seconds. Disconnection resumes the previous fast fallback; RPC failures also resume fast checks. Repeated transport failures mark the link offline after ten seconds, while retaining the recent-screen grace period used by checkout. Request matching, publisher ownership, signature retry, saved-answer acknowledgment and thank-you timing remain intact.
- Menu, pricing, settings, hardware, payment configuration, workspace membership and service edits increment a workspace runtime revision. Registers fetch promptly after notifications, reconnect or visibility return, with a 15-minute fallback. Applying data requires an idle register with no checkout/update blockers and unchanged activity revision before/after the request. A local one-second eligibility timer makes no server requests by itself; failed reads are throttled to at most once per 15 seconds.
- Routine CRM events become eligible hourly. The hourly cohort drains through the existing signed pg_net outbox, including retries and continuation after acknowledgments; new routine events wait for the next hourly pass. Consent changes attempt immediate delivery and retry in the minute maintenance pass. Claims serialize and prevent concurrent deliveries for the same customer. Customer snapshot consent fields are refreshed from the authoritative customer record at claim time, so older queued snapshots cannot restore a prior opt-in. Event IDs, HMAC signing, five-minute leases and delivery history remain in use.
- The minute CRM maintenance job collects async responses before leases expire and continues eligible deliveries. It does not call a Next/Vercel route. With no eligible work it performs only database checks. Inbound signed marketing removals remain immediate.

Migrations: `20261206080000_stage_two_live_refresh.sql` and `20261206090000_stage_two_hourly_crm.sql`. They are additive and support older clients. New browser notification clients fall back to polling if subscription cannot be established. Notification RLS requires POS permission in the row's workspace; browsers cannot write signals. Raw screen/customer/payment tables are not added to Realtime.

Validation covers shared-request concurrency and action-time invalidation; real PostgreSQL heartbeat suppression, response persistence, publisher ownership, RLS, consent priority, old-snapshot consent, async acknowledgment and retries; and actual React browser display reconnect/signature/menu-during-checkout behavior. Hosted staging verifies authenticated Realtime and shared order polling before release. No test charges or payouts are needed for this stage.

Stage 3 remains separate: capture held approved cards with saved tips when closing the credit-card batch. Nightly capture backup and hourly payout processing remain unchanged here.
